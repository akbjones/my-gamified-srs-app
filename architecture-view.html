Patterns the pipeline relies on

1. Parse → Edit → Write (never regex on .ts source) Every "apply fixes" script uses the same dance: splitFile() finds the dict literal, vm.runInNewContext('({' + body + '})') parses it as a JS object, the script edits the object, serializeDict() writes it back. Robust against odd characters in source words (apostrophes, Cyrillic, Devanagari).
2. Resume by side effect Long audits write incremental progress to *.jsonl/.json after every 5 batches. On rerun, they skip entries already in the file. Tolerates API rate limits and Ctrl-C without losing work.
3. Card-centric vs Dict-centric audits ai-card-audit.py walks deck → dict (does the entry match how this card uses it?). ai-polysemy-audit.py walks dict → reality (does the entry list all common meanings of this word?). The bill/check polysemy bug existed because the first kind of audit can't see meanings the deck doesn't exemplify.
4. Real lookupWord everywhere The audit pipeline imports the actual production lookupWord from each dictionary file. So if hyphen handling, elisions, or verb form resolution change, audits automatically reflect what the user sees. No regex re-implementations of lookup logic.
5. Stanza as ground truth, not gospel Stanza's POS/lemma analysis seeds the dictionary but is treated as a hint — discrepancies become STANZA_LEMMA_MISMATCH audit issues, not silent overwrites.

C. How the two halves connect

The runtime app never calls any pipeline scripts. The pipeline produces frozen artifacts (.ts, .json, .mp3) which Vite bundles into dist/. The app gets the result; the user's phone doesn't run Stanza or Claude.

If a user taps "⚑ flag as wrong" inside WordPopover, the issue goes to Netlify Forms (a separate channel). It's then a manual review step that may feed the next pipeline iteration — but that's a human-in-the-loop step, not an automated one.
